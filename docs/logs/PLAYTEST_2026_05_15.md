# Playtest investigation, 2026-05-15

Patrick's read after testing all four modes against the same songs:

- ML-light: best feel
- ML-full: worse than ML-light despite cleaner per-stem onsets
- ML-max: worse than ML-full, with visibly lower density and slider-heavy feel

This doc captures what the cache and an instrumented pipeline trace
say about why, plus concrete fixes ranked by impact and effort.

## Empirical baseline (single song, expert)

Same cached audio (`alUDEBR-znU.wav`, 168s) generated under three modes:

| Mode      | Notes | Taps | Holds | Hold% | NPS  |
|-----------|------:|-----:|------:|------:|-----:|
| ML-light  |   898 |  809 |    89 |  9.9% | 5.35 |
| ML-full   |   913 |  822 |    91 | 10.0% | 5.43 |
| ML-max    |   692 |  623 |    69 | 10.0% | 4.12 |

Lane distribution and inter-note gap distribution are nearly identical
between ML-light and ML-full (both ~53/47 L/R, gaps 0.63s/0.61s/0.75s/0.73s
vs 0.64s/0.64s/0.73s/0.73s). ML-max shows 30-40% larger gaps across all
lanes, consistent with the lower density.

## Pipeline trace, ML-full vs ML-max, same song @ expert

```

```

The `desired_total` (target NPS * duration) is identical, which is correct.
What differs is `n_candidates_into_thinner` and the resulting `keep_ratio`:

- ML-full has 1068 candidates and would want `ratio = 1.16` to hit
  1244 notes. The 0.98 cap clips this, the chart lands at 916 (a few sanity
  drops in dense moments).
- ML-max has **1488 candidates** because of MERT's chorus subdivisions
  (`halves_in_chorus` + `quarters_in_chorus` at Expert). The calibrator
  computes `ratio = 0.84`, applies it globally, and `n_keep = 0.84 * 1488
  = 1250`. The sanity cap then deletes **512 notes** (vs 131 in ML-full)
  before the chart settles at 732.

## Why ML-max ends up sparser than ML-full

It's a self-cancelling pair: MERT adds chorus subdivisions, and the
sanity cap immediately deletes them. The chart loses notes anyway
because of how `_calibrated_ratio` is computed in `difficulty.py:217`.

The keep ratio is a **single number per song**:

```python
ratio = desired_total / n_candidates
```

Adding 288 chorus subdivisions to `n_candidates` drops the ratio from
1.16 (clamped at 0.98) to 0.84. That 0.84 then applies to the **whole
song**, including verses that never received any subdivisions. Verses
lose 14% of their notes for free.

Then the sanity cap (`SANITY_NOTES_PER_WINDOW = 8` over a 1s window)
kicks in during choruses, deleting most of the MERT subdivisions that
just inflated `n_candidates`. Choruses end up at roughly the same density
they would have had in ML-full (the cap dominates). Verses do not
recover the 14% they lost.

Net result: ML-max produces a sparser chart than ML-full while paying
the full MERT cost.

## Why ML-max feels slider-heavy

Hold rate is fixed at 10% per Expert tuning, so the absolute proportion
of holds-to-taps is unchanged. Two things drive the perception:

1. **Sparse tap context makes each hold visually dominant.** At 4.12 NPS
   the chart has roughly one note every 240ms; a 0.5-1.2s hold spans 2-5
   taps' worth of screen time. In a 5.43 NPS chart, the same hold spans
   3-7 taps' worth.

2. **`detect_holds` picks longer holds in sparser charts.** The candidate
   filter uses `next_in_lane[idx] - n.t` as the maximum hold horizon
   (`hold_detect.py:124`). In a sparser chart, the next same-lane note
   is further away, so the horizon is larger, more taps qualify as hold
   candidates, and the top-K-by-sustain-duration ranking picks longer
   ones. A hold that would have been clipped to 0.3s in ML-full because
   the next same-lane note arrived can stretch to 0.8s in ML-max.

## Why ML-full ≈ ML-light but feels worse

The cache says these two modes produce statistically near-identical
charts: 898 vs 913 notes, 9.9% vs 10.0% holds, 53.3% vs 54.8% left-hand
lane share, gap distributions within ~3% of each other.

The lane assignment path is centroid-driven only; stem tags are
informational (per the 2026-05-12 revert in `docs/DECISIONS.md`).

So the felt-worse signal is most likely **which specific onsets get
detected**, not how many or which lane they land in. Per-stem detection
catches things the full-mix detector misses (a quiet snare buried under
vocals) and drops things the full-mix detector caught (a bright synth
attack that doesn't show in either drums or vocals stem; the full-mix
residual pass is supposed to catch this but its dedupe gate against
per-stem onsets removes some). Plus, the centroid value per onset is
sampled **from the stem's own spectral centroid**, not the full mix,
which biases the median cutoff and therefore the band split.

Caveat: this hypothesis is not yet confirmed by data; lane distributions
match between the two modes, so any centroid bias is washing out in
aggregate. The actual divergence may be more subtle (timing, specific
onset substitution).

## Recommended fixes, ranked

### Fix 1 (HIGH IMPACT, EASY) - Make `_calibrated_ratio` discount synthetic candidates

The root cause of ML-max sparsity. Subdivisions are bonus material, not
real musical events; they should not penalize the keep ratio for the
real onsets.

Location: `backend/app/pipeline/difficulty.py:217-230`.

Sketch:

```python
def _calibrated_ratio(
    *,
    difficulty: str,
    n_candidates: int,
    n_real_candidates: int,   # new arg
    duration_s: float,
) -> float:
    lo, hi = TARGET_NOTES_PER_SEC[difficulty]
    target_mid = 0.5 * (lo + hi)
    if n_real_candidates <= 0 or duration_s <= 0:
        return 0.5
    desired_total = target_mid * duration_s
    # Calibrate against real onsets so synthetic subdivisions don't
    # inflate n_candidates and pull the ratio down for the whole song.
    ratio = desired_total / n_real_candidates
    return max(_MIN_RATIO, min(_MAX_RATIO, ratio))
```

Caller passes `n_real_candidates` by counting onsets whose strength is
above SYNTH_STRENGTH (0.40 marker). `shape_difficulty` plumbs this
through; `chart_builder.py` doesn't need to change.

Expected effect on the test song: ML-max keep_ratio rises from 0.84
back toward 0.98 (capped), final note count rises from ~732 toward
~916. Verse density matches ML-full. Chorus density still gets capped
by `_enforce_sanity_cap` so chorus stays at ~8 NPS ceiling, exactly
what we want.

Validation: re-run the same song through ML-max with this change. The
final note count should land within 5% of ML-full's count.

### Fix 2 (HIGH IMPACT, EASY) - Skip MERT subdivisions in already-dense beats

Even with Fix 1, MERT adds 288 chorus subdivisions that the sanity cap
deletes. Compute waste, but more importantly the kept notes that DO
survive sanity-cap are sometimes synthetic when a real-onset note
nearby got bumped (because they have nearby times, the score-sort can
pick the synthetic one if it scored higher). Better to never add them.

Location: `backend/app/pipeline/beat_fill.py:259-273` (half-beat) and
`:278-300` (quarter-beat).

Sketch: gate `halves_in_chorus` and `quarters_in_chorus` on real onset
density at that beat. If real_per_beat[i] >= 3 (the beat is already
dense), skip the chorus subdivisions for that beat.

```python
place_half = (
    rules["halves_everywhere"]
    or (rules["halves_in_dense"] and in_dense_section)
    or (rules["halves_in_chorus"] and in_chorus and real_per_beat[i] < 3)
    or in_crescendo
)
```

Expected effect: ML-max chorus subdiv_added drops from ~266 toward
~100. Combined with Fix 1, ML-max chart count rises further AND the
note pattern in choruses contains more real-onset events.

### Fix 3 (MEDIUM IMPACT, EASY) - Cap hold horizon at a fixed beat fraction

Sparse charts shouldn't generate long holds just because the next
same-lane note is far away. The musical sustain that justifies a hold
is determined by the AUDIO, not by chart layout.

Location: `backend/app/pipeline/hold_detect.py:124`.

```python
# Before:
horizon = min(n.t + max_hold_s, next_in_lane[idx] - LANE_NEXT_SAFETY_S)

# After: same-lane horizon capped at 2 beats so sparse charts don't
# manufacture long holds out of large lane gaps.
two_beat_horizon = n.t + 2.0 * (beat_period_s or 0.5)
horizon = min(
    n.t + max_hold_s,
    next_in_lane[idx] - LANE_NEXT_SAFETY_S,
    two_beat_horizon,
)
```

Expected effect: in ML-max, holds that currently stretch to 1+ seconds
get clipped to ~0.8s (at 150 BPM). Hold percentage stays at 10% but
each hold is shorter, releasing screen time back to subsequent taps.

### Fix 4 (LOW IMPACT, EASY) - Sanity cap awareness in chorus subdivision

If you keep MERT subdivision but want to spend its compute well:
budget subdivisions per beat from the cap. The 8 notes/sec cap over a
1s window divided by 4 lanes gives 2 notes/lane/sec. A beat at 150 BPM
is 0.4s, so the per-beat budget is roughly 8 * 0.4 = 3.2 notes. If a
beat already has 3+ real onsets, the subdivision adds zero playable
value (cap deletes it). This is essentially the same idea as Fix 2 but
framed quantitatively.

### Fix 5 (LARGER, UNCERTAIN) - For ML-full felt-worse vs ML-light

This one I am not confident is the cause; it is the most-likely
hypothesis given the data and code reading.

Run an A/B with stems disabled but `USE_BEAT_THIS=1` AND
`USE_DEMUCS=1` — by passing `use_demucs=False` in `chart_builder` for
one run. If the chart matches ML-light exactly, the per-stem onset
detector is the problem, not Demucs's separation quality.

If yes, look at `onset_detect.py:154-185` (`detect_onsets_per_stem`)
versus `:60-99` (`detect_onsets`). The per-stem path runs ONE detector
per stem (energy envelope) where the full-mix path runs THREE (energy
+ CQT + harmonic-via-HPSS). Re-instate the harmonic path on the vocal
stem at least; the vocal-stem-energy detector misses melodic onsets
that the harmonic-HPSS pass would catch.

## Validation plan

1. Apply Fix 1 only. Regenerate ML-max for the same song. Confirm
   final note count is within 5% of ML-full's.
2. Apply Fix 1 + Fix 2. Confirm sanity_drops in the trace drop below
   200 (down from 512).
3. Apply Fix 3. Inspect hold durations distribution. Average hold
   duration should fall by ~20-30% with no change in hold rate.
4. Playtest one song against ML-full to see whether the "fewer sliders
   relative to taps" feel improves.
5. Save this doc's findings to `project_mode_playtest_2026_05.md`
   memory so the recommendation survives the conversation.

## What this investigation did NOT cover

- Whether `Beat This!` (used by all three ML modes) introduces beat
  drift that the librosa Baseline avoids. Patrick has not playtested
  Baseline yet in this round.
- Subjective feel of specific note patterns produced by ML-full's
  per-stem path. Lane and gap stats match ML-light, but pattern
  comparison at the note level would need a side-by-side audio overlay
  test, which `app/tools/verify_sync.py` is designed for.
- MERT label quality. The clustering produced 10 sections including 3
  "intense" sections that look plausible (8.5-23.5s, 32.5-67.5s,
  111.5-140.5s) for a song with verse-chorus structure. Label quality
  is plausibly fine; the bug is in how the labels are used downstream.
